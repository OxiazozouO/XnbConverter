## 1. 判据

「产出能不能用」的硬判据是**真的回包一次**：把产出树里**相对输入树新增/改过**的文件
（连同名 `.config`）挑出来，交给 XNB 打包器打成 XNB。打不出来的资产在游戏里一定不可用。

```bash
python tools/roundtrip-all.py          # 转一个包 → 打一个包 → 删一个包的树
```

`--chunk 500` 分批打（**按资产切**，见 `pack-check.py` 里的说明）；
`ContentHashes.json` 不算资产、不进 XNB，已从「改过的文件」里剔掉。

## 3.1 复跑（2026-10-09，写入语义改完之后）

又跑了一遍全量 32 包：**合计成功 3785 / 失败 0**，与上表**逐包相同**。

这一轮之间改了四组写入语义（`TextOperations` 分两级、`Fields` 三处、字段引用令牌两处、
`MapTiles` 逐块独立，见 `docs/research/2026-10-09-cp-write-semantics.md`）——
它们改的是**判定/计数**（写入失败 32 → 6）与部分**值**，
但产出树里「新增/改过的文件」集合没变，所以回包数字一致。
**这就是要的结论：语义订正没有把产出弄坏。**

## 4. 这个结论**不覆盖**什么

- **回包成功 ≠ 游戏里跑得对**。打包器只保证「能按声明的类型反序列化」；
  语义对不对（条件落点、值取到哪一层）由另一套核对负责
  （`docs/research/2026-10-06-condition-consumers.md` 那一族）。
- **自检仍会报、但打包器不管的**：SVE 的 `Data/FarmAnimals.StatToIncrementOnProduce` 写成空串
  （声明是 `List`）—— 实测打得出包、往返变 `null`，见
  `docs/research/2026-10-08-cp-xnb-value-dialect.md` 第 7.2 节。所以「自检 0 不符」不是本表的门槛。
- 这一轮**没有**在游戏里实地加载验证过。
