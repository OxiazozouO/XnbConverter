# 全量语料跑批快 **49%**：`AssetTypeAudit` 少了整树重扫 + 模组索引不再每包重扫

日期：2026-10-13
起因：业主看了一轮 232 包的跑批用了 **24 分 45 秒**，判断"不应该那么长时间、可能是优化没做好"。
结论：**判断对** —— 有一项自检**没有缓存**，每包都把全树重新 JSON 解析一遍。

## 0. 先量账（profile 分段 + 冷/热配对）

`SDVCP_PROFILE=1` 的分段计时（同一个只写 7 条补丁的小包，写入合计 0.06 s）：

| | wall | `AssetTypeAudit` |
|---|---|---|
| **自检缓存冷**（第一轮）| **4.97 s** | **1921 ms** |
| 自检缓存热（第二、三轮）| **1.95 / 1.88 s** | **46 ms** |

⇒ 每包的固定开销里，这一项独占 **~1.9 s**，而且**与那包写了多少无关** ——
`AssetTypeAudit` 枚举全树一万多份 `.config`，每份 **JSON 解析两遍**（产出那份 + 原版那份）
= **两万多次 `JObject.Parse`**，每次都跑。232 包 ⇒ **≈ 7.3 分钟**。

（订正一次我自己的错判：先以为这 1.9 s 是**冷盘 IO**，因为"热缓存下旧二进制也只有 46 ms" ——
但那个"旧二进制"其实**已经含了**当时的改动，是我拷贝的时机不对。冷/热对照把它定死了：
**同一份代码**冷缓存 1921 ms、热缓存 46 ms ⇒ 是反复重算，不是 IO。）

其它固定开销（量出来的）：**进程启动 ≈ 1.2 s/包**（小树 1.44 s、全树 1.74 s ⇒ 树只多 ~0.3 s），
232 包 ≈ 4.6 分钟 —— 这一档要在"多包一进程"上做，本轮没动。

## 1. 改法

`AssetTypeAudit` 接入既有的 **`AuditCache`**（别的自检早就用了 ✓ 只有它漏了）：
按产出路径记「这份 `.config` 上次的结论 ✓ + 有没有 findings ✓」，
**调度用的"这一轮写过哪些"取落盘账本**（`OutputTree.PlannedWrites` 里筛 `.config` ✓）——
写过的必须重算、没写过的必然没变（这就是"先对要操作的文件做汇总"那份账本）。

只改自检，**不碰任何产物**。

## 2. 验证

- 测试：**1433 条全绿**（行为无变化 ⇒ 无新测试；正确性靠下面两柱）；
- 受控对比（同参数 232 包，prof97 → prof99）：
  · **报告：231 包完全相同**（补丁级 0 变化）
  · **产出树：逐文件相同**（`✅ 两棵树逐文件相同`）
- 墙钟：

| | 累计 | 平均 |
|---|---|---|
| 改前（prof97）| **1485 s = 24 分 45 秒** | 6.4 s/包 |
| 改后（prof99，只加自检缓存）| **978 s = 16 分 18 秒** | 4.2 s/包 |
| 再改后（prof100，+ 模组索引复用/缓存）| **757 s = 12 分 37 秒** | 3.3 s/包 |

⇒ **−49%**（−12 分钟）。第一刀的 −8.5 分钟与"每包省 1.9 s × 231 包 ≈ 7.3 分钟"一致，
第二刀的 −3.7 分钟与"每包 1.44 → 0.33 s × 231 ≈ 4.3 分钟"一致（另 1 分钟是波动 ——
这台机器单跑能差 30%，所以每刀都同时给了**每包配对的机制证据**）。

两刀过完同参数对比都一样干净：**报告 231 包完全相同 + 产出树逐文件相同**（prof99 与 prof100 都核过）。

## 2.5 第二刀：模组索引**一进程一份** + 可选磁盘缓存（16 分 18 秒 → **12 分 37 秒**）

接着量"剩下的固定开销"，用 `--mods` 指一个空目录做对照：

| | wall（同一个只写 7 条补丁的小包）|
|---|---|
| 全参数 | **1.48 s** |
| `--mods` 指空目录 | **0.33 s** |

⇒ 固定开销**全部**来自「递归扫 Mods 树」这一件事（本机十万量级文件项 ⇒ ~0.6 s/次），
而一次 `convert` 里它被建了 **2~4 次**（主流程 / `BuildTokenResolver` / Include 求值 / 烘焙各一次）
—— 每个包再来一个新进程 ⇒ **232 包白扫几百次**。SMAPI 自己每次启动也只扫一遍。

两处改动：
1. `ModIndexProvider`：**一进程一份**（按目录缓存，只读、无副作用）；
2. `--mod-index-cache <路径>`：把扫的结果落盘复用（**工具链显式 opt-in** —— 不传就是每次真扫，
   行为与以前一模一样）。键 = Mods 目录 mtime + 一级目录数，
   ⚠ **就地改某个 manifest 的 UniqueID 不会失效**（那要逐文件 stat = 又扫一遍）；工具链不会那样改。

配对实测（同一个包，交替三组）：

| | 最快 |
|---|---|
| 改前（每包真扫 2~4 次）| 1.44 s |
| 一进程一份 | **0.69 s** |
| 一进程一份 + 磁盘缓存 | **0.33 s**（= 上面"空目录"那个上界）|

⚠ 顺带试过、**又撤掉**的一条：把 `EnumerateFiles(..., "manifest.json", AllDirectories)`
换成枚举目录再看 `manifest.json` 在不在 —— 语义等价、条目数少一个量级，但实测**略慢**
（1.59 s vs 1.43 s）：那 0.6 s 是**目录遍历本身**（一万多个目录的元数据），不是筛名字 ⇒ 撤了。

## 3. 一处**试过又撤掉**的改动（记下来免得重做）

顺手也把"这份文档里有没有 CP 令牌"改成**按资产记一次的单调标记**（省掉每条补丁的整档扫描，
SVE 上 `EditData.写` 5427 → 4974 ms，约 0.45 s/包）。

⚠ 它**改变了产物落盘的时机**：标记是**保守**的（宁可说"有"），于是有些本来走"快路"的文档
被推去走 i18n 路 ⇒ 链条中途自检看到的资产数 **+1** ⇒ 30 个包的报告与改前不一致（树最终仍相同）。
实测省下 0.45 s、换来报告不一致 ⇒ **不值，撤了**（`PatchApplier` 里留了注释说明为什么别这么干）。

⇒ 教训：**自检的计数也是报告的一部分**，任何"改变走哪条路"的优化都要过同参数对比这一关。
