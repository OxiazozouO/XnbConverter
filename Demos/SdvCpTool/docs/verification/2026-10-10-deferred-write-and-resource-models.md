**基线**：`D:\tmp\tmx_e\32_*/tree`（旧行为 —— 每包一棵产出树、每个补丁立即读改写真资源）
**对照**：`D:\tmp\tmx_v5\tree`（共用一棵树 + `--append` + 延迟写 + 地图/图片内存模型 + 两级只读缓存）

## 为什么要做这件事

用户给的方向：**「先对语法树需要操作的文件做汇总，再在产出阶段操作最少的资源达到相同的目的」**
—— 判定/规划阶段是纯算法、不碰资源；同一份资源只解码/解析一次、改动累积在内存、最后统一写回。

落地成三层：

| 层 | 位置 | 作用 |
|---|---|---|
| 延迟写 | `OutputTree`（`deferWrites`） | 所有写入先进内存，跑完 `Flush()` 一次落盘 |
| 目标内存模型 | `ImageCache` / `MapCache` | 同一张图/地图读一次、改在内存、最后写一次 |
| 只读缓存 | `ImageCache.TryReadSource` / `MapCache.TryGetSource` / `MapCache.TileSheetRefIndex` / `OutputTree.GetConfigFacts` | 内容包里的源文件、全树扫描结果、`.config` 候选特征，整个运行只读一次 |

规模（实测本语料）：

- `EditImage` **862** 条打在 **274** 个目标上，**133** 个目标被多条改（`LooseSprites/Cursors` 一张 **107** 次）
- `EditMap` **802** 条打在 **122** 个目标上，**80** 个目标被多条改（`Maps/Town` **81** 次）
- 新资产选 `.config` 模板时要把整个目录的候选比一遍：`Data/` 有 **263** 份候选（含 1.2 MB 的 `Shops.json`）

## 查出的三类真实差异（都不是「优化」而是**正确性**问题）

### 1. 延迟写让「同一次运行里刚写的」在磁盘上不存在

`Load` 一张图 → 紧接着 `EditImage` 同一目标：目标图还在暂存里，磁盘上没有，
`EditImage` 直接读盘 ⇒ 误判「目标不存在」，**整条不写**。
地图同理（`Load` 的 `.tbin` 走 `StageBytes`）。实测 SVE 丢了 **19 条**（6 张 Junimo 图 + 1 张立绘 + 12 张地图）。

**修法**：图片/地图的读一律走内存模型（`ImageCache.TryGetPixels` / `MapCache.TryGetModel`），
缓存优先、回落到产出树的**暂存感知**读（`OutputTree.ReadBytesOrNull`）。

### 2. 暂存字典用序号比较 ⇒ 大小写变体各占一个槽位

产出文件系统是 Windows，`Characters/Dialogue/Andy.json` 与 `characters/dialogue/andy.json`
是**同一个文件**。立即写时谁赢由**调用顺序**定；延迟写之后同一个文件在字典里分成多个槽位，
谁赢改由 `Flush()` 的**字典序**定。

实测 SVE 的一条 `Load`（Target 45 项 × FromFile 50 项的逗号笛卡尔积）把同一份对话按三种大小写
写了 10 次，最后落盘的是 4 键那份（612 字符），137 键那份被盖掉 —— **100 个文件**对不上旧基线
（`Characters/Dialogue/*` 46、`Data/*` 42、`Strings/*` 9、`Maps/*` 2、`ContentHashes.json` 1）。

**修法**：`OutputTree` 的三个暂存字典与 `MapCache._entries` 全部改用
`StringComparer.OrdinalIgnoreCase`。

### 3. 「只读过、最后没改成的」地图被重新序列化写回

`MapCache.Flush()` 原本把所有加载过的地图都写一遍。补丁**失败**时模型只是被读过，
重新序列化会写出一份与原文件不逐字节相同的 tbin。**修法**：`Entry.Dirty`，只有改成功的才写。

### 4. 同一张地图的第二条补丁读不到第一遍的成果

第一条改成功后暂存被撤（落盘权归缓存），第二条再去读盘就什么都读不到 ⇒
误报「地图 tbin 不在资源树里」。实测 SVE 的 `Maps/Custom_EnchantedGrove #100`
与 `Maps/Custom_ShearwaterBridge #139` 就是这么丢的（旧基线它们写成功过）。
**修法**：`MapCache.TryGetModel` —— **缓存优先**，没有才去读。

## 追加一轮：`Load` 的 `.tmx` 也收进内存模型

`LoadMapTmx` 原本自己 `File.Move` 写产出树里的 `.tbin` —— 产出树里的地图就有了**两个写手**
（它 + `MapCache.Flush`）。改成回读校验写在**产出树之外**的系统临时目录、转出来的模型交给
`MapCache.Set`，由缓存统一落盘。

这一改带来一处**目录项大小写**差异（同一张图在 A/C 两版里分别叫 `Beach-Nightmarket.tbin`
与 `Beach-NightMarket.tbin`，md5 相同）。

**根因**：Windows 上往**已存在**的文件里写**不会改名字** —— 所以目录项的大小写由
**第一次创建它的那次写**决定。SVE 正是先 `Load Maps/Beach-Nightmarket`（小写 m，这次是它创建了文件）、
后 `EditMap Maps/Beach-NightMarket`（大写，只是改内容）。而 `Load` 的字节还在产出树暂存里时，
`MapCache` 建条目只见到 `EditMap` 那条大写名字，落盘就成了大写。

⚠ 我第一版把它理解成「跟随**最后一次**写」并写了 `Entry.Rel`，结果是**反的**：
它把 Trellis 三张图的大小写也带跑了（A 是 `(Stage N)`、那一版成了 `(stage N)`）。
A/B 逐文件比一跑就露馅 —— 这也是为什么每次改完必须做同参数对比，不能靠推理。

**修法**：`OutputTree.PendingName(rel)` 给出「这条路径在暂存里首次出现时的写法」，
`MapCache` 建条目时优先用它；`ImageCache` 那边本来就是这个行为（字典键留首次写法），不动。

## 性能：把「每条补丁都重算一遍」的地方收掉

⚠ **先测准**。这台机器的墙钟噪声大到**同一份二进制两次跑 135s vs 82s**（差 65%），
拿墙钟数字判断优化有没有用会得出完全相反的结论。改成量 **CPU 时间**
（`Process.TotalProcessorTime`，`SDVCP_PROFILE=1` 打开）后两次跑的偏差在 3% 以内。

单跑 SVE（最大的包）拿到的账，以及逐项处置：

| 热点 | 改前 CPU | 改后 CPU | 处置 |
|---|---|---|---|
| `Load` 阶段 | 49.2s（墙钟）| **3.4s** | `LoadApplier.FindMapConfig` 是 **O(N²)**：外层遍历 `InputFiles`、内层再 `Contains` 一次线性查找。13506 条 × 数千 `.config`。换成 O(1) 集合查询；另给 `.config` 建了「按祖先目录」索引 |
| `EditData` 阶段 | 17.8s | **8.1s** | 同一条链上**四遍**全量拷贝：`_rawCache.Get` 深拷贝 → `ToString(None)` → `Parse` → `EditDataMerger` 内部又深拷贝。前两步去掉（合并基础改成直接用缓存里已解析的原文，隔离由 `Apply` 内部那次克隆保证），`Set` 也不再深拷贝（所有权转移） |
| `ShapeAudit` | 4.0s | **0.22s** | 与 `ConditionPlacementAudit` 都把「产出 + 原版」各解析一遍（合起来 4 遍全树解析）。加 `AuditParseCache` 共享，同一份文件只解析一次 |
| 待落 JSON 的序列化 | — | — | 大资产（1 MB 上下）每条补丁 `ToString` 一遍 → 改成 `StageJson` **落盘时才序列化一次**（中途有人读文本就懒序列化并留用） |

另外加了 `--no-audit`：那几道自检的代价与**树的大小**成正比、与这一包改了多少无关 ——
逐包各跑一遍等于把同一批文件解析 32 遍。链式跑语料时只有**最后一个包**需要它们
（那会儿的树才是最终产物），`convert-mods.py` 默认给中间包传 `--no-audit`
（要逐包都看就传 `--audit-all`）。⚠ 跳过时中间包报告里那几段是空的，别拿它当自检结论。

**全量 32 包**（同一台机器，前三个数是优化前的三次实测）：

| 版本 | 用时 | 产出树 |
|---|---|---|
| 优化前 | 8m44s / 10m42s / 11m03s | — |
| 只做上面那几项 | 4m46s | 与 A 逐文件相同 ✓ |
| 再加 `--no-audit` | 1m46s | 与 A 逐文件相同 ✓（账目也一致：7048 / 3848 / 9）|
| 再把落盘与整树拷贝并行 | 1m39s | 与 E 逐文件相同 ✓ |
| 再把 i18n 的逐语言整文档克隆收掉 | 1m22.8s（`--fast`）| 与 E 逐文件相同 ✓ |
| 再把全树自检做成**增量**（默认路径）| **1m37s** | 与 J 逐文件相同 ✓，六段自检也逐包一致 ✓ |

### 全树自检的增量缓存：把「跨进程」那一层也补上

跳过自检能省 60%（3m28s → 1m22s），但那几个分析脚本（`corpus-diff.py` /
`unexpanded-tokens.py` / `token-blocked-patches.py`）要**逐包**读报告里那几段 ——
偷偷跳过会让它们的统计**少算而不报错**，所以默认不能跳。

真正的浪费是：链式跑语料时**每个包是一个独立进程**，进程内的 `AuditParseCache` 帮不到跨包，
每个包仍要把整棵树重新解析一遍。补一个 `AuditCache`（键 = 文件长度 + 最后写入时间），
把每个文件的结论记在**这一轮产出根目录**下的一个文件里，与这一轮的树同生共死。

单包实测（热缓存）：ConditionAudit 3468→265ms、ShapeAudit 328→46ms、
GameDataAudit 1500→15ms、KeyCase 203→62ms。**整轮 3m28s → 1m49s**，报告仍是完整的 ✓。

⚠ 这个缓存靠「大小 + 时间」判新鲜度，所以本轮之外手工改过产出树再复用同一个缓存文件会拿到过期
结论 —— 它是**这一轮的一次性产物**，别跨轮搬。

### i18n：一条补丁曾克隆 9 份整文档

`WriteLocalized` 为**每个语言**各 `Apply` 一次，而 `Apply` 内部 `data.DeepClone()` 一份整文档。
实测「聚宝盆制作」那一包改的是 `Data/Objects`（**三万多个节点**）、9 个语言 × 43 条补丁 ——
单条补丁 400 ms，光这一包就 17 秒 CPU。

改成：**克隆一次**，在克隆体上收集所有含 `{{i18n:...}}` 的节点及其原值，
之后每个语言只把这批节点从原值重放一遍，改完**立刻序列化**（各语言共用同一份工作副本，
交 token 的话它们到 Flush 会序列化成同一份内容 —— 测试逮到过）。
产出与逐语言克隆**逐字节相同**，那一包的 EditData 从 18.7 s 降到 7.0 s。

落盘那一层本来就是「一堆**互不相干**的目标文件」—— 文本 / JSON / 二进制 / 拷贝四批，
加上图片重编码、地图序列化，各写各的。`OutputTree.WriteBatch`、`ImageCache.Flush`、
`MapCache.Flush` 改成 `Parallel.ForEach`，**账本仍按排序后的顺序登记**（只有写动作并行），
所以 `FlushedFiles` 的顺序与串行时一致、复现性不受影响。整树拷贝同理（一万多个文件、600 MB）。

**确定性**：并行落盘之后，用同一份二进制把全量 32 包跑了两遍，两棵树 13506 个文件
逐字节相同 ✓ —— 写动作并行、但目标路径两两不同，账本顺序也仍是字典序。

**自检缓存改由落盘账本判新鲜度**之后，又收了几处：`SpriteSheetValidator` 拿贴图尺寸不再
`Png.Read`（会把整张图解出来），改读 IHDR 头 24 字节；未展开令牌自检与键大小写冲突自检
也接上增量缓存（前者贵在逐字符串扫全树，后者贵在 `Data/` 那几份一两 MB 的）。

⚠ **一次没成的尝试**：试过「有缓存就不枚举整棵树、改遍历『账本 ∪ 缓存』」，想着省掉那 230 ms
的头一次枚举 —— 实测**没有可测量的收益**（1.80s → 1.78s），却把 `conditionPlacement.checkedAssets`
数错了（2762 → 2876）。已回滚。教训：省时间不多的改动，不值得去动「数得对不对」这条线。

### 这一轮踩到的两个坑（都记在这里，别再犯）

1. **`--no-audit` 的 `else {` 锚错了行**：我把开关插在 `auditParseCache` 那行，而那行在
   `output.Flush()` **之前** —— 跳过自检时连**落盘一起跳了**。32 个包全没写，树里只剩
   香草副本的 7595 个文件（基线 13506），而用时 1m31s 看起来"快得漂亮"。
   **是逐文件对比把它抓出来的**：`只在 A 5912`。教训：性能对比必须同时看**正确性**，
   否则「变快了」可能就是「没干活」。

2. **`ConditionPlacementAudit` 排在 `Flush()` 之前**：写是立即的时候排哪儿都一样；
   改成延迟写之后，它扫到的是**上一包的状态**而不是本包产出。已挪到 `Flush()` 之后。
   这个不影响产出树（只影响报告），所以逐字节对比抓不到 —— 是**读代码**时对出来的。

3. **`_pendingJson` 与另外三种暂存形态没有互斥**：`StageJson` 是后加的，
   `WriteText`/`StageBytes`/`StageCopy` 都没把它清掉 —— 同一路径既进了文本又进了 JSON 时，
   `Flush` 里 JSON 排在后面写，会把后设的文本盖回去。实测表现：`Characters/Dialogue/*.json`
   变成 `{}`。已四处补齐互斥，并加了回归测试。

4. **文件名的大小写不能靠落盘批次顺序决定**。SVE 先 `Load Data/Events/JojaMart`（大写）、
   后有几十条 `EditData data/events/jojamart`（小写）：两者原先落在同一个暂存字典里，
   键保留首次写法 ⇒ 大写 ✓；改成文本/JSON 分开暂存后分属两个字典，
   名字就由**落盘批次顺序**（文本 → JSON）决定了 ⇒ 小写。按 Windows 的真实规则显式化：
   `OutputTree._displayPath` 记下**第一次写它的那次**的写法，落盘统一按它取路径。

## 未确证 / 待办

- **计时没有做过受控对比**：上面的三个数出自三次不同时刻的运行，机器同时还在跑别的活。
  只敢说「比每包一棵树快得多」，不敢说精确倍数。
- 「定点写变化区域」在 PNG 这层**做不到**：PNG 字节按行紧密排布（还有 zlib 流与滤波器），
  改一个像素也得整张重编码。这里定点的只是「解码/重编码各一次」，别把它说成「只写变化区域」。
- 三条既有失败（`Data/Events` 的 `$query` 取不到旧值、`EditImage` 目标不存在等）与本次改动无关，
  旧基线同样有。
