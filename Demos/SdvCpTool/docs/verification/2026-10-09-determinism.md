# 产出是**确定**的：同参数跑两遍，逐字节相同

日期：2026-10-09

**为什么要核**：所有「改动前后对比」都默认「同样的输入 + 同样的代码 ⇒ 同样的输出」。
一旦有哪一步依赖了 `Dictionary`/`HashSet` 的迭代顺序、时间戳、临时路径，
对比出来的差就分不清是代码改的还是随机的。

**怎么核**：同一个包、同样的参数，跑两遍，把两棵产出树**逐文件比 sha1**。

|---|---|---|---|

## 2. 补全：全 32 包（2026-10-09 晚）

⚠ 首轮只核了 5 个包，文档里明写着「**没核到的包不能假定也确定**」。这一节把它补上。

两轮**全量**（32 包），**两轮之间没有改过 Release exe** ——
这是前提：这里测的是「同一份代码、同一份输入，跑两遍一样不一样」，
不是「改了代码产出变没变」（那是**受控对比**，另一回事）。

```
包数 32, 文件合计 248804
只在A 0 / 只在B 0 / 内容不同 0
```

⇒ **32 包、248804 个文件，逐文件比 sha1，全部一致**。
（逐包输出见脚本；每个包都是 `OK`。）

## 3. 10-10 改动之后的再确认（全量逐字节，**跑完了**）

10-10 那轮动了音频注入的接线（`PatchJudge` / `WritePolicy` / `PatchApplier` / `Program`）
与 `AudioChangesMerger`，所以又跑了两遍全量确认没引入不确定性。

```
A 249014 个文件，B 249014 个文件
只在 A：0    只在 B：0    内容不同：0
```

⇒ **32 包、249014 个文件，逐文件比 sha1，全部一致。**

⚠ 补记一段过程（免得下次又照着错的办法来）：
一开始用**单线程** Python 算 sha1，全量两棵树约 46 GB，**跑一刻钟没完就中断了**，
于是当时只做了分层验证（写入资产集合 + 单包逐字节），并把「这轮没跑完全量」写进文档。
后来写了 `tools/compare-trees-by-hash.py`（**`ProcessPoolExecutor` 多进程**），
同样的两棵树几分钟就跑完了 —— 结论也跟着从「严格说没做完」变成**做完了**。

## 覆盖到了哪些路径

光跑「没发射的包」不够 —— 还得确认**真的走到了发射器**。按两遍中任一份报告的统计：

```
SVE        seasonalEmission  groups=127 emitted=52 rejected=75 patchesCovered=208
           appearanceEmission groups=17 emitted=2 rejected=15 patchesCovered=12
SVE 季节性服装  tilesheetEmission groups=55 emitted=1 rejected=54 patchesCovered=4
```

⇒ 四季发射（52 组 / 208 条）、立绘发射（2 组）、图集发射（1 组）**都实际产出过**，
两遍逐字节一致 ⇒ 这些自研发射器也是确定的。

## 没覆盖到的

- ~~只核了 5 个包~~ → **已补全到 32 包**（见 §2）；
- `report.json` 里有 `generatedAt` 时间戳，两遍必然不同，**没有**把它算进差异（核的是产出树）；
- 没核**跨机/跨运行环境**的确定性（只核了同一台机器上的两次运行）；
- **没核「不同并行度」**：两轮都是 `CORPUS_JOBS=4`。并行只影响**调度**、不影响单包内的写入顺序，
  但这一条是**推理**不是实测 —— 标「未确证」。
