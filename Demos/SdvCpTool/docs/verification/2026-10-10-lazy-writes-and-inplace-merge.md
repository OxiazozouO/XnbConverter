# 两处「白做」的整文档拷贝：按语言展开的变体、以及 EditData 的克隆

日期：2026-10-10（接 `2026-10-10-deferred-write-and-resource-models.md`）

上一轮把「读一次 / 写一次」铺到了图片、地图、文本、二进制、拷贝五条路上；这一轮接着往下，
盯的是**同一份文档在一轮里被反复整份复制/序列化**的两处。

---

## 先说测量：细粒度计时不能再拿 CPU 时间当尺子

`Process.TotalProcessorTime` 的粒度是系统时钟节拍（这台机器 **15.6 ms**）。分段计时 `Lap`
是用它做差分的，而单条补丁里那几步常常只有几毫秒 —— 一次 3 ms 的合并会被记成 0 或 15，
一轮语料 2400 多次取样归出来的「哪个动作贵」纯属噪声。实测同一份二进制两次跑、
同一个包的同一项能差 **60%**（`EditData.合并` 2471 vs 3669 ms）。

- 细粒度改用 `Stopwatch.GetTimestamp()`（`Prof.Now()` / `Prof.AddSince`）；
- **整段**（`Phase`）仍用 CPU 时间 —— 跨轮墙钟能差 65%，整轮的数字只能看 CPU；
- ⚠ 这台机器**同一份二进制两次跑整体也能差 30%**（`--fast` 全量：83s / 120s 都有过）。
  所以下面所有结论都来自**新旧交替各 3 轮**的配对比较，**不看单跑数字**。

顺带修了两个取数工具自己的毛病（都在 `tools/convert-mods.py`）：

1. 子进程输出按 `utf-8` 解 —— 实际是 **GBK**，中文全变成替换符；
2. `capture_output=True` 把分段计时（写在 stderr 上）整个吞掉 —— 跑了一整轮，profile 一条没留下。

## 落点 1：按语言展开的变体，每条补丁都把整文档序列化一遍

`聚宝盆 制作` 一包实测 **720 次**变体序列化 = 4214 ms；而真正落盘的只有
**9 个资产 × 9 个语言 = 81 份** —— `Data/Objects` 被 **39** 条补丁连着改、`Data/Machines` **29** 条，
只有最后一次的变体留在账上（`TryWriteText` 覆盖）。**89% 是白做的。**

做法：`OutputTree.StageLazyText(rel, Func<string>)` —— 与 `StageJson` 同一个路子，
**内容也推迟到落盘才生成**；同一路径后来的写入连生成函数一起顶掉。
生成函数自己负责把共享文档**还原**成基础语言（基础资产与各变体共用同一份 token，
不还原就会互相覆盖）。中途有人读这条路径时就地生成一次并留用（不会生成两遍）。

## 落点 2：EditData 每条补丁克隆整份文档

```
合并.整文档克隆   1658 ms / 108 次        ← 大资产上这就是全部开销
合并.真合并         13 ms / 106 次        ← 真合并不值钱
```

做法：`EditDataMerger.Apply(..., takeOwnership: true)` **原地改**，`PatchApplier` 只在
「失败不需要回滚」的场合才交所有权。为此得先让整条流水线**先验后改**，补了三处：

1. **`TextOperationMerger`**：解析期那级校验（形状非法 ⇒ 整条补丁不创建）提到了所有改动之前。
   原先是一边验一边改 —— 坏操作排在中间时，它**前面**那几条已经改进去了，失败后留下的是
   「改到一半」的文档。这一条同时更贴 CP：`TryParseTextOperations` 本来就是在补丁创建前验整张表。
2. **`TranslationApplier.WriteLocalized`**：`CoerceAsset`（结构标量归一，就地改）原先是第一件事，
   而「资产含 `{{i18n:…}}` 但包内没有可用翻译」的失败在它**之后**才返回 —— 于是调用方那份
   被改过却按失败处理。现在改成：非 i18n 路径照旧；i18n 路径先在**克隆体**上归一、再翻译
   （翻译只动克隆体），**全部成功之后**才回头归一调用方那份。产出逐字节不变。
3. **`Descend(create: true)`（`TargetField` 的下降）**：新建的容器**先不挂上去，走通整条路径才挂**。
   原来是边建边挂 —— `["White Cow","Skins","X"]` 会先把 `Skins` 建成空列表（模型说是 `List`），
   再去空列表里找 `X`，找不到就整条失败，而那个空 `Skins` **已经留在调用方的文档里了**。
4. **`PatchApplier` 的那道闸**（唯一还在拦的情形）：条件落点**多于一条**时，
   后一条落不下去会留下前一条的改动（`ConditionWriter.Apply` 自己是「先定位、后落笔」，
   所以**单落点**放行）。
5. 还有一个必须拦的：`paths.Count == 0` 那条路**不写盘、也不更新原文缓存**。原地改会让
   「报成空操作」的内容从产出树的暂存里漏出去 —— 暂存的那个对象与原文缓存是**同一个**。

## 证据

1. **全量 32 包、默认模式（含全部自检）**：改动前后 **产出树 13506 个文件逐字节相同**、
   **32 份报告逐项相同**（只差 `generatedAt` 与产出根路径）。
2. `--fast` 全量同样逐字节相同。
3. 单测 **1284 通过 / 0 失败**（新增 11 条：原地改不留痕、懒文本只生成最后一次、
   与其它暂存形态互斥、中途读就地生成、TextOperation 中途非法不留痕）。
4. **配对计时**（5 个 i18n 重的包、`--fast`、新旧交替各 3 轮）。
   下表的「合计」是把两版二进制各拷一份、**交替**跑出来的（`SDVCP_EXE` 指过去）：

   | 轮 | HEAD（改前） | 本轮改完 |
   |---|---|---|
   | 1 | 68.7s | 55.1s |
   | 2 | 66.3s | 55.6s |
   | 3 | 65.4s | 55.4s |
   | 均值 | **66.8s** | **55.4s** |

   **每一对都是新的快**；均值 **−17%**，而新版三轮只差 0.5s（这轮机器是空的；
   中途带负载跑过一次，新旧都被拖慢、数字不能用 —— 这也是为什么要配对交替）。
   单项（同一份 profile 口径下）：`EditData.写` 12914 → 6824 ms、
   `EditData.合并` 27141 → 16378 ms、`Write.克隆+收集i18n点` 10174 → 0
   （拆成 `Write.克隆` 4843 + `CoerceAsset` 370 + 收集 301）。
   原地改覆盖面：**2373 是 / 13 否（多落点条件）**（共 2386 条）。

5. **整树定点回包**（`tools/pack-check.py`，产出相对输入新增/改过 **6461** 个文件、小树 7009 个）：
   **成功 3486 / 失败 0**。这是"产出能不能用"的硬判据那一侧的一次独立复验。

## 还剩什么（如实记，别当成已经收了）

- **`Write.克隆`（i18n 路径）**：i18n 资产必须同时留「原文（带令牌，`RawAssetCache` 合并要用）」
  与「译文（产出要用）」两份 —— 这一份克隆是**结构性**的，不是白做。
- **树拷贝 ~2.5 s**：`robocopy /MT:32` 实测 5.0 s，现在这版并行拷已经比它快，别再折腾。
- **`落盘` 16.1 s（CPU 口径）**：写 13506 个文件 + PNG 重编码，属 IO / 编码本身。
- `ConditionAudit` 4.0 s、`判定` 4.2 s：前者只在最后一个包跑（`--fast` 时），后者是静态分析。

## 未确证

- 配对计时的**绝对值**不可比：这台机器带负载时单跑能差 30%（同一份二进制 83s 与 120s 都出现过），
  上面那两个均值只说明「新的更快」，别拿去当「全量一轮 X 秒」的结论。
